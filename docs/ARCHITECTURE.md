# Text Yourself v1 architecture

This document records the decisions, assumptions, and trade-offs agreed before the
one-shot v1 implementation. `AGENTS.md` remains the authoritative platform contract.

## Product boundary

Text Yourself is a private household app for keeping topic-oriented conversations.
It borrows the familiar rhythm of a texting client without trying to become a
real-time communication product.

V1 includes:

- shared topics with archive and rename actions;
- authored text messages containing safe, clickable links;
- one-level quoted replies;
- author-only message edits and soft deletion;
- household-wide search of topic titles and message bodies;
- a complete browser-side mirror for offline reading and search;
- queued offline creates and edits, replayed idempotently when connectivity returns;
- five-second foreground polling plus an explicit **Sync** control;
- installable PWA metadata and an offline app shell.

V1 deliberately excludes attachments, fetched link previews, reactions, private
topics, participant lists, unread counts, push notifications, and permanent deletion.

## System shape

- **Web:** React, TypeScript, and Vite. IndexedDB is accessed through Dexie. A
  generated service worker precaches the application shell.
- **API:** FastAPI with a small domain/service layer and PostgreSQL repositories.
- **Database:** PostgreSQL owned solely by this app. All data rows are shared within
  one household and protected by forced row-level security.
- **Delivery:** one multi-stage arm64 container serves both API and built web assets.
  Deployment follows `AGENTS.md` exactly; the host deploy script owns migrations,
  health gating, rollback, and registration.

The server is authoritative. IndexedDB is a durable local projection and outbox,
not a second source of truth.

## Identity and authorization

There is no application login and no user table.

- `AUTH_MODE=proxy` trusts identity and role headers injected by the loopback-only
  reverse proxy. Only `editor` and `viewer` roles are recognized.
- `USER_DISPLAY_NAMES` is an SSM-provided JSON object mapping permitted email
  identities to household-facing display labels. An identity absent from the map is
  rejected in proxy mode.
- `AUTH_MODE=none` uses synthetic, configurable development identity values and
  defaults to `user@example.com` / `You` / `editor`.
- Viewers can read and sync. Editors can create topics and messages. Only a
  message's author can edit or soft-delete it. Any editor can rename or archive a
  topic.

Every request transaction sets `app.household_id` and `app.user_id` from trusted
server identity context before accessing RLS-protected rows.

## Data model and synchronization

IDs are UUIDs generated by the browser for offline-capable creates. Replaying a
create with the same ID is idempotent.

### `topics`

- `id`, `household_id`, `created_by`
- `title`
- `archived_at`, `created_at`, `updated_at`
- `sync_version`

### `messages`

- `id`, `household_id`, `topic_id`, `author_id`
- `body`, `reply_to_id`
- `created_at`, `updated_at`, `edited_at`, `deleted_at`
- `sync_version`

A database sequence assigns a unique, increasing `sync_version` on every insert or
update. `GET /api/sync?after=<version>&limit=<bounded>` merges topic and message
changes in version order. Soft deletion means every mutation remains representable
without a separate tombstone table. The browser follows pages until `has_more` is
false, so it eventually mirrors the complete database without any unbounded API.

List and search endpoints are also cursor-paginated. The initial UI may hydrate all
sync pages into IndexedDB, but no single database query or HTTP response is unbounded.

## Mutation and conflict policy

- Offline mutations enter a durable outbox before the UI considers them pending.
- Creates are idempotent by client UUID.
- The outbox preserves mutation order and stops on a permanent conflict so the UI
  can explain what needs attention.
- Updates use last-write-wins at the server. This is an explicit household-scale
  trade-off: it keeps offline behavior understandable without building a conflict
  resolution UI. Server timestamps and author rules still apply.
- A server-confirmed entity always replaces its optimistic local projection.
- Deleted message bodies remain in PostgreSQL for recovery/audit but are never
  returned to clients after deletion; clients receive a deleted placeholder.

## Search and links

Online search uses PostgreSQL full-text search over topic titles and live message
bodies, with bounded results. Offline search scans the complete local IndexedDB
projection. Given household scale, normalized substring matching is preferred to a
second browser search-index dependency.

URLs are detected from message text and rendered as safe external links showing the
domain and URL. The server never fetches them in v1. This avoids tracking leakage,
timeouts, and server-side request forgery risk.

## API outline

- `GET /healthz`
- `GET /api/me`
- `GET /api/sync?after=&limit=`
- `GET /api/topics?cursor=&limit=&archived=`
- `POST /api/topics`
- `PATCH /api/topics/{topic_id}`
- `GET /api/topics/{topic_id}/messages?cursor=&limit=`
- `POST /api/topics/{topic_id}/messages`
- `PATCH /api/messages/{message_id}`
- `DELETE /api/messages/{message_id}`
- `GET /api/search?q=&cursor=&limit=`

Mutation bodies and responses use ISO-8601 UTC timestamps and UUID strings. API
errors use a stable machine-readable code plus a plain-language message.

## Visual direction

The interface is a calm household memory stream rather than an iMessage clone.

- **Palette:** midnight `#162433`, lake `#176B73`, mist `#E8EEF1`, cloud `#F7F9FA`,
  ember `#E8795A`, and white `#FFFFFF`, with equivalent dark-mode tokens.
- **Type:** a restrained Charter/Georgia serif for topic titles; a humanist system
  sans stack for messages and controls; tabular system numerals for timestamps.
- **Layout:** full-screen topic list or conversation on phones; a stable topic rail
  beside the active conversation from tablet widths upward.
- **Signature:** each topic gets a deterministic color "thread mark" derived from
  its UUID. The mark repeats in the list, header, and reply rail, making topics feel
  distinct without decorative clutter.
- **Motion:** one short message-settle transition, disabled by reduced-motion
  preference. Offline, pending, failed, and syncing states are conveyed with text and
  shape, never color alone.

The app is fully usable at 380px, supports keyboard navigation, visible focus,
semantic controls, appropriate live regions, and device light/dark preference.

## Operational assumptions

- GitHub repository: `mephistophyles/text-yourself`.
- App name and unique platform slug: `Text Yourself` / `text-yourself`.
- Container port: `8000`, published only as `127.0.0.1:8000:8000`.
- Runtime memory ceiling: 512 MB.
- Required app SSM parameters: `DATABASE_URL`, `AUTH_MODE`, `PUBLIC_BASE_URL`, and
  `USER_DISPLAY_NAMES`; `HOUSEHOLD_ID` comes only from `/home/shared/`.
- License: MIT.
- CI builds but does not deploy pull requests. A push to `main` runs tests, builds the
  commit-SHA image, and invokes the platform deploy contract.

## Accepted trade-offs

1. Polling and manual sync use more small requests than WebSockets but are easier to
   operate and sufficient for a non-chat household tool.
2. Mirroring all history improves offline usability but increases initial sync time
   and browser storage. Bounded paging and visible progress keep this controlled;
   incremental syncs are cheap after the first load.
3. Offline last-write-wins can overwrite a concurrent edit. With two cooperative
   users and message-author-only edits, the risk is lower than the complexity of a
   merge interface.
4. Link previews are less rich, but unfetched links are safer and work offline.
5. Soft deletion consumes storage, but preserves precious data and makes sync
   reliable. Permanent purging is an operational task outside v1.
